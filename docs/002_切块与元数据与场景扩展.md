## 需求 1：问答应用后续场景（报告撰写 / 内容生成 / 审核）

### 1.1 事实：现状

- 应用能力在 `backend/app/applications.py`：节点种类 `start | knowledge | llm | condition | template | output`。  
- 前端模板仅三种（`Applications.tsx` `templateInfo`）：知识问答、文案改写、规则分流。  
- 运行产 `application_run`（逐步 output / sources / tokens），**不**进入 `LogsPage` 的 source 枚举。  
- 在线对话 `Chat` + RAG：`backend/app/rag.py` 流式问答与来源引用。  
- 一期企划明确不做合同审查 AI 等（见需求确认清单）；此处「审核」指**基于已入库制度/契约的人工确认型审核辅助**，不是上合同审查大模型产品。

### 1.2 场景能力清单（建议产品能力，非已实现）

#### 场景 A：报告撰写

| 能力 | 说明 | 优先级 |
|------|------|--------|
| A1 选题与大纲 | 用户给题目/对象，生成可编辑大纲（章节勾选） | P0 |
| A2 按章检索 | 每章独立 knowledge 检索，带 kb 范围与 topK | P0 |
| A3 章稿生成 | llm 基于 `{{context}}` 写章；缺依据可停（已有 `requireEvidence`） | P0 |
| A4 合并排版 | template/output 拼目录、正文、来源表 | P0 |
| A5 来源附录 | 自动列出 chunk 引用（doc/version/location） | P0 |
| A6 多轮改稿 | 对某一章追加指令再生成，保留版本 | P1 |
| A7 导出 | md/docx（导出格式待验证现有能力；当前应用仅返回文本） | P1 |

#### 场景 B：内容生成

| 能力 | 说明 | 优先级 |
|------|------|--------|
| B1 多风格改写 | 通知/邮件/对客话术等预设 prompt 包 | P0 |
| B2 批量条数 | 一次输入多条，循环 llm（需新增「批处理」或列表变量；现状无） | P1 |
| B3 知识回写建议 | 生成结果可「建议入库」走审核，不直接写向量 | P1 |
| B4 变量表单 | 开始节点收集字段（产品名、受众、禁忌语） | P0 |
| B5 敏感词/长度规则 | condition 或本地规则节点（无外呼） | P1 |

#### 场景 C：审核

| 能力 | 说明 | 优先级 |
|------|------|--------|
| C1 送审材料 | 上传或粘贴待审文本 + 选择制度知识库 | P0 |
| C2 条款对照 | knowledge 检索相关条款；输出「原文片段 ↔ 制度片段」对照表 | P0 |
| C3 风险点列表 | llm 给出风险点、级别、建议改法；每条绑来源 | P0 |
| C4 人工确认 | 审核人勾选通过/驳回/需修改；写审计记录 | P0 |
| C5 不自动裁决 | 文案固定：系统只提供依据，结论由人确认（对齐验收口径 #7） | P0 |
| C6 与协同例外联动 | 可选：驳回时在协同例外留一条（二期） | P2 |

### 1.3 原型 / 产品怎么扩（不写业务黑话）

**观点：优先「模板 + 少量新节点」，不要先上新运行时。**

1. **应用生成页**增加三张场景卡（与现有三模板并列）：  
   - 报告撰写  
   - 内容生成  
   - 制度对照审核  
2. 每张卡一键生成**预设节点图**（仍用现有 KINDS）：  
   - 报告：`start → llm(大纲) → knowledge → llm(章) → template → output`（一期可用单次「整篇」简化；多章循环标为二期）。  
   - 内容生成：`start → llm → template → output`（关闭 requireEvidence）。  
   - 审核：`start → knowledge → llm(对照与风险) → output`，结果区增加「人工确认」假按钮（原型）/ 真实确认 API（实现）。  
3. **运行结果区**增加 Tab：正文 | 来源对照 | 确认记录。  
4. **侧栏**：使用者默认可见「应用生成」已有；场景卡主要给管理人员配置后发布。  
5. **观测**：运行写入统一 Trace（见 `002_可观测模块设计_知枢.md`），否则审核追责缺少证据链。

### 1.4 建议接口（实现期）

```
POST /api/applications/{id}/runs          # 已有
POST /api/applications/{id}/runs/{runId}/review
  body: { decision: "pass"|"reject"|"revise", comment, checklist[] }
GET  /api/applications/templates          # 可选：服务端下发场景模板，避免只存在前端
```

## 需求 2：切块 — 父子切分 / 语义切分（可调 LLM）

### 2.1 事实：现状

| 项 | 实际 |
|----|------|
| 切分实现 | `backend/app/parsers.py` `_split` → `RecursiveCharacterTextSplitter` |
| 参数 | `chunk_size=size`（导入传入），`chunk_overlap=min(80, size//8)` 写死 |
| 入口 | 上传 Form `chunkSize`（200–1500），`ingestion.py` |
| UI | 导入向导 Slider「建议片段长度」；知识库配置写死文案「按标题与语义结构」 |
| 索引 | `rag.py` `index_document`：一 chunk 一向量；payload 无父子关系 |
| 检索 mode | `hybrid` / `semantic` / `keyword` 指**检索**方式，不是切块方式 |

**结论**：无父子切分；无 LLM 语义切分；UI「语义结构」与实现不一致（见缺口清单 B2）。

### 2.2 缺口

| 缺口 | 影响 |
|------|------|
| 无 parent/child | 小块召回准但回答缺上下文，或大块噪声多 |
| 无 semantic LLM split | 规章/纪要跨句被切断；表格后叙述粘连差 |
| 策略不可配置 | 只能调长度；无法按知识库类型选策略 |
| 文案超前 | 配置页声称已有语义结构分段 |

### 2.3 建议配置项（知识库级 + 单次导入可覆盖）

```yaml
chunking:
  mode: recursive | parent_child | semantic_llm   # 默认 recursive（保持兼容）
  chunkSize: 600                                  # 已有
  chunkOverlap: 80                                # 新，替代写死
  # parent_child
  parentSize: 2000
  childSize: 400
  parentOverlap: 100
  # semantic_llm
  semanticModelConfigId: null                     # 类型 LLM；空则禁用该 mode
  semanticPromptVersion: "v1"
  maxSemanticCallsPerDoc: 40                      # 费用护栏
  fallbackOnError: recursive                      # LLM 失败回退
```

### 2.4 建议接口与数据形状

**上传/任务 options（扩展现有）**

```
POST /api/knowledge-bases/{kbId}/documents
  form: ...现有...
        chunkMode=parent_child
        chunkSize=400
        parentSize=2000
        chunkOverlap=80
        semanticModelConfigId=...
```

**Chunk 扩展字段（写入 draftChunks/chunks）**

```json
{
  "id": "child-uuid",
  "title": "...",
  "content": "...",
  "location": "...",
  "kind": "text",
  "parentId": "parent-uuid",
  "role": "child",
  "splitter": "parent_child",
  "splitterMeta": {"parentSize": 2000, "childSize": 400}
}
```

父块可只存 SQL、不进向量，或进稀疏索引；子块进 Qdrant。检索命中 child 后拼 parent 内容进 prompt（`prepare_generation` 处扩展）。

**语义切分（观点流程）**

1. 先按标题/空行切成「段候选」。  
2. LLM 返回边界 JSON（起止句或段落索引）；校验长度与覆盖率。  
3. 失败或超调用上限 → `fallbackOnError`。  
4. usage 记入 import log steps（meter=cloud）。

**检索 API**：保持现有；增加可选 `expandParent=true`（默认 true when mode=parent_child）。

### 2.5 原型怎么表现

导入设置步增加：

- 分段方式：字符递归（当前）| 父子分段 | 语义分段（需模型）  
- 选语义时：模型下拉 + 费用提示「将按文档段落调用模型」  
- 预览：假数据展示父块灰底、子块列表  

知识库配置「分段方式」改为读取真实配置，去掉写死「按标题与语义结构」。

## 需求 3：导入后元数据构建

### 3.1 事实：现状

- 文档有：`name`、`kind`、`size`、`version`（替换升版整数）、`status`、`chunks`、`warnings`、系统时间戳。  
- 解析 meta 多为版面：`page`/`pages`/`bbox`/`sheet`/`rowStart`/`rowEnd`/`parser`。  
- **没有**自动抽取：业务时间、业务版本号、主体、负责人、检索关键词列表、可能被问到的问题。  
- `integrations/README.md` 写明：local-vault 的 Claude 元数据增强未作为中台功能开放。  
- 检索：向量 + jieba/BM25 对正文；Qdrant payload 无自定义元数据过滤。

### 3.2 目标字段（文档级 `doc.metadata` + 可选 chunk 继承）

| 字段 | 类型 | 用途 | 抽取来源优先级 |
|------|------|------|----------------|
| `docDate` | date \| null | 时效过滤、排序 | 文内日期 → 文件属性 → 空 |
| `bizVersion` | string \| null | 展示「制度 V2.1」 | 文内版本行 → 文件名 → 空 |
| `subject` | string \| null | 主体（公司/项目/产品） | LLM/规则 → 空 |
| `ownerPerson` | string \| null | 负责人 | 文内「编制/责任人」→ 空 |
| `keywords` | string[] | 关键词检索加权 / 过滤 | LLM + 词法 → 至少文件名分词 |
| `likelyQuestions` | string[] | 问题索引（可向量化） | LLM 生成 5–15 条 |
| `extractedAt` | iso | 抽取时间 | 系统 |
| `extractor` | `{mode, modelConfigId?}` | 审计 | 系统 |
| `confidence` | number \| null | 人工复核排序 | 模型自估，可空 |

另：**系统字段不混用**——`version`（发布次数）与 `bizVersion`（业务版本）分开。

### 3.3 抽取时机

```text
上传成功
  → 解析正文 / 出 draftChunks
  → 【新】元数据抽取任务（可与向量化并行或先于发布）
       - mode=off | rules | llm
       - 写入 doc.metadata（草稿态）
       - 待检查页展示可编辑
  → 人工可改 keywords / likelyQuestions
  → 发布索引时：
       - 正文 chunks 照旧向量化
       - 额外：每个 likelyQuestion 生成「问题向量」指向 docId（或独立 payload kind=question）
       - keywords 写入 payload 供 keyword/filter
```

失败策略：抽取失败不阻断解析；`metadata.status=failed` + 警告；发布仍可用纯正文。

### 3.4 存哪

| 层 | 存什么 |
|----|--------|
| SQL Entity `doc.payload.metadata` | 完整可编辑元数据（真源） |
| Qdrant payload | `docDate`、`bizVersion`、`subject`、`ownerPerson`、`keywords`（短字段）；`chunkRole` |
| 可选派生实体 `doc_question` | `likelyQuestions` 文本 + 向量 id，便于单独管理 |

不建议只存在浏览器原型；后端真源与观测一致。

### 3.5 怎么检索

1. **问题索引**：用户 query 先对 `likelyQuestions` 向量/关键词命中 → 带高权重回文档，再取正文 chunks。  
2. **过滤**：API 增加 `filters: { subject, ownerPerson, docDateFrom, docDateTo, keywordsAny }`。  
3. **混合打分**：BM25 对 keywords 字段加权（观点：关键词权重大于正文稀有词时可降幻觉召回）。  
4. **UI**：检索测试与对话高级选项增加过滤器；文档预览页增加「元数据」Tab（可改、可重抽）。

### 3.6 建议 API

```
POST /api/documents/{id}/metadata/extract
  body: { mode: "rules"|"llm", modelConfigId?: string }
PATCH /api/documents/{id}/metadata
  body: { docDate, bizVersion, subject, ownerPerson, keywords, likelyQuestions }
# 发布沿用现有 publish；index 阶段读 metadata
```

### 3.7 原型区块文案

文档预览新增 Tab「元数据」：

- 时间 / 版本 / 主体 / 负责人（输入框）  
- 检索关键词（标签）  
- 可能被问到的问题（列表，可增删）  
- 按钮：重新抽取（模拟） / 保存  

导入设置增加：`导入后自动抽取元数据` 开关 + 模式选择。

## 三者关系（观点）

```text
更好的切块（父子/语义）→ 片段质量
更好的元数据（含问题索引）→ 找得到、滤得准
场景模板（报告/生成/审核）→ 用得起来
可观测 → 出问题时能回到某次切块/抽取/生成
```

没有元数据与切块，报告/审核场景只会「像能用」；没有场景模板，中台停留在「能问一句」。
