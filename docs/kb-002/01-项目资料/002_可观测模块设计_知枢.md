## 0. 事实 vs 观点

### 事实（现状）

- 已有页面：`frontend/src/pages/Operations.tsx` → `LogsPage`（侧栏「日志与监测」，View=`logs`）。
- 日志实体：`kind=log`，来源 `source ∈ {chat, retrieval, import}`（见 `frontend/src/types.ts` `LogEntry`；`Operations.tsx` `sourceLabels`）。
- 对话/检索写 log：`backend/app/rag.py`（`_base_log` / `_finish_chat` / retrieve）。
- 导入写 log：`backend/app/ingestion.py`（`source: "import"`，含 `steps`/`usage`/`taskId`）。
- 应用运行：**不写** `log`，写 `kind=application_run`（`backend/app/applications.py` `_persist_run`），仅在应用详情内查看。
- 用量原则已立：供应商未返回则显示「未知」，不伪造 0（README / Logs 文案）。
- 产品内尚无 Agent / Tool / Skill / Harness 运行时；`.agents/skills/` 为开发态技能包。

### 观点

- 应先做「统一观测壳 + 四类 Timeline」，再预留 Agent 子页；避免空造 Agent 中心却连应用运行都搜不到。
- UI 命名建议用「运行观测」而不是「可观测性平台」，对业务用户更直观。

### 1.1 侧栏

扩展为分组（文案可直接给前端假数据页）：

```

  ├ 运行观测          ← 新建总览（推荐默认进这里）
```

## 2. 功能设计（四条观测线）

### 2.1 知识库构建过程

**用户问题**：这份文件卡在哪？花了多少钱？切出多少块？为何没发布？

**页面区块（知识构建流水）**

1. **筛选条**：知识库、状态（处理中/待检查/成功/失败）、时间范围、任务 ID。  
2. **流水表**：文件名、知识库、阶段、进度、耗时、tokens（已知/未知）、操作「打开时间线」。  
3. **时间线抽屉**（核心）：

| 阶段 | 展示字段 |
|------|----------|
| 接收上传 | sha256、大小、是否替换版本、`replaceDocumentId` |
| 解析 | parser=auto/cloud、DocMind 任务 ID、警告列表 |
| 切块 | chunk 数、chunkSize、策略名（现状写 `recursive_character`；未来 parent_child / semantic_llm） |
| 图意理解 | vision 调用次数、tokens |
| 向量化 | embedding 模型、维度、collection、indexVersion |
| 发布切换 | 旧 version → 新 version、是否 autoPublish |
| 失败/取消 | error、可重试标记 |

**数据来源（现状可接）**

- `task` entity + `log` where `source=import`（`ingestion.py`）。  
- 缺口：阶段枚举未标准化；建议事件模型见 §3。

### 2.2 对话日志（增强现有）

**保留** LogsPage 表格与详情抽屉。

**增强项**

| 项 | 说明 |
|----|------|
| 关联 Trace | 详情顶栏增加 `traceId`（可先等于 requestId） |
| 来源扩展 | `source` 增加 `application`（从 application_run 投影或双写） |
| 命中片段 | 详情增加 sources 摘要（doc 名 + location），不只 steps |
| 会话跳转 | 有 `sessionId` 时「打开对话」 |

### 2.3 Agent 调用过程（含工具 / Skill / Harness）

**事实**：当前无 Agent 运行时 → 页面先做信息架构与假数据，文案标明「演示数据」。

**列表页字段**

- runId / 状态 / Agent 名或应用名 / 触发方式（对话、应用、手动）/ 起止时间 / 总 tokens / 错误摘要  

**详情页（必须覆盖需求所列）**

| 观测点 | UI 区块 | 字段 |
|--------|---------|------|
| 单次输入 | 「输入」卡片 | messages[] 或 input 文本、附件引用 |
| 单次输出 | 「输出」卡片 | final output、结构化结果 JSON |
| 运行状态 | 顶部 StatusPill + 状态历史 | queued / running / waiting_tool / waiting_human / succeeded / failed / cancelled |
| 工具调用 | 「工具」时间线 | toolName、args、result 摘要、latency、error |
| Skill 调用 | 「Skill」时间线 | skillId、version、入参、出参、是否命中缓存 |
| 单次 token | 「用量」条 | input/output/total；未知显「未知」 |
| 调用上下文 | 「上下文」 | kbIds、modelConfigId、temperature、检索 query、trace 父节点 |
| Harness 异常 | 「异常」 | harnessStage、exceptionType、message、stack 摘要、是否可重试 |

**与应用生成的关系（观点）**

- 短期：把 `application_run.steps` 映射为「简易 Agent 轨迹」（节点≈步骤，无 tool）。  
- 中期：若引入真正 Agent，再增加 tool/skill span，同一 `traceId`。

### 2.4 计费消耗

**页面区块**

1. **概览卡**：本周期已知 tokens、未知条数、预估费用（无价表时显示「未配置单价」）、按模型 Top。  
2. **明细表**：时间、来源、模型、input/output/total、meter=local|cloud、归属知识库/应用。  
3. **规则说明**：本地 embedding/jieba 不计云费用；缺失 usage 不按字数估算（与现网一致）。  
4. **导出**：CSV（沿用 Logs 导出思路，防公式注入）。

**价表（配置，可后做）**

- `settings` 或独立 `pricing`：provider + modelId → 元/1K input、元/1K output。  
- 无价表时只展示 tokens，不编造人民币。

## 3. 事件模型（建议）

### 3.1 核心对象

```text
Trace
  traceId          string   # 建议全局
  rootType         enum     # import | chat | retrieval | application | agent
  rootId           string   # taskId / requestId / runId
  owner            string   # 会话 owner，不用浏览器自称角色
  startedAt        iso
  endedAt          iso?
  status           enum
  attrs            object   # kbIds, appId, ...

Span
  spanId           string
  traceId          string
  parentSpanId     string?
  name             string   # parse | split | embed | retrieve | rerank | llm | tool | skill | harness
  kind             enum     # internal | llm | embedding | retriever | tool | skill | parser
  status           enum
  startedAt / endedAt
  tokens           {input, output, total} | nulls
  meter            local | cloud | unknown
  model            string?
  error            {type, message}?
  attrs            object   # chunkCount, toolName, skillId, harnessStage, ...

UsageRollup (可物化或查询聚合)
  day, modelId, source, tokensKnown, tokensUnknownCount, estimatedCost?
```

### 3.2 与现有实体映射

| 现有 | 映射 |
|------|------|
| `log` (chat/retrieval/import) | 一条 Trace + steps[] → Span |
| `task` | import Trace 的进度投影 |
| `application_run` | Trace(rootType=application)；steps → Span |
| 未来 agent_run | Trace(rootType=agent) |

### 3.3 API 草图（实现阶段）

```
GET  /api/observability/overview
GET  /api/observability/traces?rootType=&status=&kbId=&from=&to=
GET  /api/observability/traces/{traceId}
GET  /api/observability/usage?groupBy=model|day|source
```

CSRF / 角色：写操作仍走现有 security；观测只读接口 `require_manager` / admin，chat 详情按 owner 过滤。

## 4. 建议原型新增页面（假数据足够前端照加）

> 下列为文案与区块结构；本机编码若已改结构，以其为准。

### 4.1 侧栏入口文案

- 图标建议：`Activity` 或 `ChartNoAxesCombined`  
- 文案：**运行观测**  
- 副标题（可选 tooltip）：看清构建、问答、应用与用量  

### 4.2 页面：运行观测（总览）

**页头**

- eyebrow: `OBSERVABILITY`  
- 标题：运行观测  
- 描述：从知识入库到一次回答，把状态、依据和用量放在同一处。  

**区块**

1. 四指标卡：今日请求、构建失败数、已知 Tokens、P95 耗时  
2. 「需要处理」列表：失败导入、降级检索、应用运行失败（各最多 5 条）  
3. 「最近轨迹」表：时间、类型标签（构建/对话/检索/应用/Agent）、摘要、状态、Tokens  
4. 空态（无 Agent 时）：Agent 追踪仍显示入口，说明「尚未接入 Agent 运行时，下方为界面示意」

**假数据示例（可直接塞 baseline）**

```json
{
  "metrics": {"requestsToday": 128, "buildFailures": 2, "tokensKnown": 932110, "p95Sec": 3.42},
  "recent": [
    {"traceId": "tr_demo_1", "rootType": "import", "title": "导入《差旅报销制度》", "status": "success", "tokens": 12040},
    {"traceId": "tr_demo_2", "rootType": "chat", "title": "出差住宿标准是多少？", "status": "success", "tokens": 1860},
    {"traceId": "tr_demo_3", "rootType": "application", "title": "应用「知识问答」运行", "status": "failed", "tokens": null},
    {"traceId": "tr_demo_4", "rootType": "agent", "title": "（示意）报告撰写 Agent", "status": "waiting_tool", "tokens": 4200}
  ]
}
```

### 4.3 页面：知识构建流水

**区块**：筛选条 → 任务表 → 抽屉时间线（§2.1 阶段）。  
抽屉底部：「打开文档片段」「打开导入任务」。

### 4.4 页面：Agent 追踪（示意）

**列表** + **详情双栏**：

- 左：状态历史  
- 右 Tab：输入输出 | 工具 | Skill | 用量 | 上下文 | 异常  

假数据需包含一次成功 tool 调用与一次 Harness 异常，便于评审字段是否够用。

**Harness 异常示意文案**

- 类型：`HarnessTimeout`  
- 阶段：`tool_result_validate`  
- 说明：工具返回超过 30s 未通过结构校验  
- 动作：重试 / 标记人工处理  

### 4.5 页面：用量与计费

**区块**：周期切换（7/30 天）→ 概览卡 → 按模型柱状/条 → 明细表 → 「单价未配置」Alert。

### 4.6 现有 LogsPage 微调文案（建议）

- 标题改为：对话与检索日志  
- 来源筛选项增加：应用运行（即使一期用跳转 application_run 列表实现）  
- 详情增加 Trace 链接：查看完整轨迹

## 5. 与开源参考的边界

| 参考 | 可借鉴 | 不在本阶段做 |
|------|--------|--------------|
| Langfuse | Trace/Span/Generation 模型、LLM 输入输出对照 | 不上外置 SaaS 除非客户要求 |
| Phoenix | 检索评估与 span 可视化 | 不替换现有 rag-workbench 评测 |
| OpenTelemetry | 属性命名、context 传播 | 不先上全量 OTLP 基建 |

观点：第一期用业务库存 Trace/Span（或先把 steps 规范化）即可；等调用量上来再导出 OTLP。

## 6. 落地顺序（建议）

1. 统一 `traceId`，application_run 进入观测列表（半周级）。  
2. 知识构建时间线（复用 import log steps，标准化阶段名）。  
3. 用量页（只聚合已知 tokens + 未知计数）。  
4. Agent 假数据页进原型，等运行时再接线。
